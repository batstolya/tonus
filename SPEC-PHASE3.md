# Tonus — ТЗ фаза 3: Google-вход, Google Calendar и мобильная версия

Продолжение `SPEC.md` и `SPEC-HUB.md`. Фазы 1–2 реализованы. Здесь — вход через Google, подключение Google Calendar как источника событий для карты стресса, и мобильная версия всего сайта.

---

## 0. Что нового

- Вход на сайт через **Google-аккаунт** в дополнение к существующему логину/паролю.
- **Google Calendar** как живой источник событий для карты стресса — вместе с cal.com и загрузкой `.ics`.
- **Мобильная версия** всего сайта.

## 1. Аутентификация: логин/пароль + Google

- Реализуется через Supabase Auth: включить провайдер Google рядом с уже работающим email/паролем.
- Оба метода сосуществуют. Если пользователь регистрировался по email, а затем вошёл через Google с тем же адресом — связать identities (account linking), чтобы это был один аккаунт.
- Вход через Google использует только базовые scope (`openid`, `email`, `profile`) — это **не** sensitive-доступ, верификация Google не нужна.

### Настройка (один раз)
- Google Cloud Console: создать проект, настроить OAuth consent screen, создать OAuth client (тип Web).
- Redirect URI — callback Supabase (+ домен приложения).
- В Supabase включить Google provider, вставить client id и secret.

## 2. Google Calendar для карты стресса

**Ключевое различие: вход через Google ≠ доступ к календарю.** Это разные разрешения, и второе сложнее.

- Чтение событий требует отдельного **sensitive-scope** `https://www.googleapis.com/auth/calendar.readonly`.
- Для постоянного (фонового) доступа нужен **offline access** с refresh-токеном, который безопасно хранится на сервере. Запрос на вход даёт короткоживущий токен; для регулярной синхронизации нужен именно refresh-токен.
- Supabase возвращает provider-токен при OAuth, но для долгого доступа к Calendar API, как правило, нужно настроить отдельный OAuth-флоу с offline access и хранить refresh-токен зашифрованно (например, в Supabase).

### Важные ограничения Google (учтены)
- `calendar.readonly` — sensitive scope. Для **публичного** приложения нужна верификация Google (проверка бренда, видео-демо флоу).
- Для **личного** использования: держать OAuth-приложение в режиме **Testing**, добавить себя тест-юзером, принять экран «unverified app». Верификация и оплата не нужны.
- Нюанс Testing-режима: refresh-токен для sensitive-доступа протухает примерно раз в 7 дней → Google Calendar нужно периодически переподключать. Альтернатива — пройти верификацию, чтобы снять ограничение.

### Поток
1. Пользователь нажимает «Подключить Google Calendar», проходит OAuth с offline access и scope `calendar.readonly`.
2. Refresh-токен сохраняется на сервере (зашифрованно).
3. При построении карты стресса за период — выборка событий через Calendar API, нормализация и сопоставление с пульсом (логика карты стресса из прошлых фаз переиспользуется).
4. На дашборде — статус подключения и время последней синхронизации; понятная подсказка, если токен протух и нужно переподключить.

## 3. Источники событий (унификация)

Карта стресса должна принимать события из нескольких источников и объединять их в один поток:

- **Загруженный `.ics`** — как в фазах 1–2 (покрывает ручной экспорт, в т.ч. cal.com).
- **cal.com** — через его `.ics`-feed (URL подписки) или API. Часто бронирования cal.com и так попадают в Google Calendar — тогда отдельное подключение не обязательно.
- **Google Calendar** — живое подключение через OAuth (раздел 2).

Каждое событие помечается источником. Одинаковые события из разных источников (например, бронь cal.com, продублированная в Google Calendar) дедуплицируются по времени/названию. Архитектуру источников сделать расширяемой — отдельный адаптер на каждый источник, общий нормализованный формат события.

## 4. Модель данных (дополнения к фазе 2)

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `connected_accounts` | подключённые внешние сервисы | user_id, provider, refresh_token (зашифр.), scopes, connected_at, last_synced_at, status |
| `calendar_events` | нормализованные события для карты стресса | user_id, source, external_id, title, start, end, is_busy, created_at |

`calendar_events` нужна, чтобы быстро строить карту стресса и дедуплицировать события, не дёргая внешние API при каждом открытии.

## 5. Мобильная версия

**Решение:** мобильная версия — это **адаптивная вёрстка + PWA**, а не отдельное нативное приложение. Это сохраняет нулевую стоимость и отсутствие сторов, выбранные в прошлых фазах, и даёт «как приложение» на телефоне (установка на домашний экран).

- Адаптив всех экранов под телефон: одноколоночные раскладки, мобильная навигация (нижняя панель), крупные тач-таргеты.
- Удобный быстрый ввод с телефона (отметить кофе/еду/настроение в пару касаний) — это основной мобильный сценарий.
- PWA: web app manifest, service worker, иконки, офлайн-оболочка, установка на домашний экран.
- Графики и таблицы — адаптировать под узкий экран (свайпы, упрощённые виды).

### Каветы
- У PWA на iOS есть ограничения (например, по фоновым пуш-уведомлениям) — для личного дашборда некритично.
- Если позже захочется полноценный нативный апп в App Store — это отдельный путь с теми же ограничениями и платой Apple, что обсуждались ранее. PWA их обходит.

## 6. Безопасность и приватность (дополнения)

- Refresh-токены Google хранить **только на сервере, зашифрованно**; никогда не передавать в браузер.
- Запрашивать минимальный scope — только `calendar.readonly`.
- Кнопка «Отключить Google» — отзыв доступа на стороне Google и удаление сохранённых токенов.
- Понятный текст на экране подключения: что именно читаем (события календаря) и зачем (карта стресса).
- Хранение токенов и данных — в регионе ЕС (GDPR).

## 7. Этапы

- **3a:** вход через Google (Supabase) рядом с логином/паролем; связывание аккаунтов.
- **3b:** подключение Google Calendar (OAuth offline) + объединение источников событий в карте стресса.
- **3c:** cal.com как источник (`.ics`-feed или API).
- **3d:** адаптив всех экранов + PWA (установка на телефон).

## 8. Чеклист настройки

- Google Cloud: проект; OAuth consent screen (тип External, статус Testing); добавить себя в тест-юзеры.
- OAuth client (Web); указать redirect URIs (callback Supabase + домен).
- Scopes: `openid`, `email`, `profile` (вход) + `calendar.readonly` (календарь, offline access).
- Supabase: включить Google provider, вставить client id/secret.
- Серверное зашифрованное хранение refresh-токена для Calendar API.

## 9. Решения к согласованию

1. Мобильная версия = адаптив + PWA, не нативное приложение. Подтвердить.
2. Google-приложение держим в Testing для личного использования (с оговоркой про ~7-дневное протухание токена календаря). Подтвердить или идти на верификацию.
3. cal.com подключаем через `.ics`-feed (проще) или API (богаче). Выбрать.
