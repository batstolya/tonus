Спецификация выглядит уже очень зрелой и близкой к реализации. Если смотреть как продуктовый архитектор, то у Tonus сейчас есть все основные контуры полноценной персональной health OS.

Я бы выделил несколько сильных сторон и несколько архитектурных рисков, которые стоит закрыть до начала масштабной разработки.

# Что уже хорошо продумано

### 1. Правильное разделение ответственности

* React отвечает только за UI и локальный парсинг.
* Supabase — источник истины.
* Gemini вызывается только через Edge Functions.
* Парсинг Apple Health происходит на клиенте.

Это снижает стоимость инфраструктуры и упрощает GDPR/privacy.

---

### 2. Верная модель данных

Особенно удачны:

* `metrics_daily` как key-value хранилище метрик;
* отдельный `heart_rate_samples`;
* отдельный `sleep_sessions`;
* отдельный слой событий (`intake_events`, препараты, заметки).

Это позволит добавлять новые метрики без миграций.

---

### 3. Исследования построены правильно

Очень важно, что:

* статистика считается детерминированно;
* Gemini только интерпретирует результаты.

То есть:

```
Данные
↓
research.ts
↓
корреляции и эффекты
↓
Gemini объясняет
```

а не:

```
Данные
↓
Gemini сам ищет закономерности
```

Это значительно снижает риск галлюцинаций.

---

### 4. Телеграм интегрирован как интерфейс, а не отдельный продукт

Правильное решение:

* один источник данных;
* сайт и бот работают с одной БД;
* бот — просто ещё один канал доступа.

---

# Самые важные пробелы

## 1. Нет слоя агрегации контекста для ИИ

Сейчас ИИ-функции перечислены отдельно:

* chat-health
* analyze-health
* biweekly-report
* telegram-bot
* deep-research

Но все они используют один и тот же контекст.

Я бы добавил:

```
health_context.ts
```

или

```
buildHealthContext()
```

---

Например:

```ts
const context = await buildHealthContext({
  userId,
  periodDays: 14
})
```

Он собирает:

* метрики
* сон
* препараты
* анализы
* заметки
* проблемы
* волосы
* события

и возвращает единый объект.

Тогда:

```ts
chat-health
analyze-health
biweekly-report
telegram-bot
deep-research
```

используют один источник данных.

Иначе через полгода логика контекста разъедется.

---

## 2. Нужен слой AI Cost Guard

Сейчас есть:

```sql
ai_usage
```

но нет механизма блокировки.

Добавил бы:

```sql
user_ai_settings
```

```sql
monthly_budget_usd
monthly_tokens_limit
```

и общий middleware:

```ts
checkBudget(userId)
```

перед каждым вызовом Gemini.

---

## 3. Нужна версия промптов

Сейчас все ИИ-функции будут хранить промпты в коде.

Через несколько месяцев возникнет вопрос:

> почему отчёт в мае был лучше чем сейчас?

Добавил бы таблицу:

```sql
ai_prompts
```

Поля:

```sql
id
name
version
prompt
created_at
```

И логировать:

```sql
prompt_version
```

в `ai_usage`.

---

## 4. Нет вычисленной таблицы готовности (Readiness)

Сейчас на дашборде есть:

> готовность дня (HRV + пульс + сон)

Но нигде не описано где она хранится.

Я бы сделал:

```sql
daily_scores
```

с колонками:

```sql
readiness
sleep_score
recovery_score
stress_score
```

и пересчитывал после импорта.

Иначе каждая страница будет считать по-своему.

---

## 5. Нет очереди фоновых задач

Сейчас:

* OCR анализов
* отчёты
* исследования

могут занимать десятки секунд.

Если пользователь загрузит:

```
15 PDF анализов
```

Edge Function может упереться в лимиты.

Я бы добавил:

```sql
background_jobs
```

с состояниями:

```sql
pending
running
completed
failed
```

Тогда:

```
upload PDF
↓
создать job
↓
worker обрабатывает
↓
готово
```

---

# Что бы я добавил в v1.1

## События на графиках

У тебя упомянуто как future.

Я бы поднял намного выше.

Причина:

без событий графики мало что объясняют.

Например:

```
HRV упал
```

и рядом:

```
🍺 алкоголь
💊 новый препарат
🧳 поездка
🤒 болезнь
```

Моментально появляется контекст.

---

## Теги событий

Расширить `intake_events`.

Сейчас:

```sql
coffee
alcohol
food
water
medicine
```

Лучше универсально:

```sql
event_type
```

и:

```sql
travel
illness
stress
workout
injury
vaccine
```

---

## Персональная базовая линия

Очень важно для исследований.

Считать:

```sql
rolling 30d baseline
```

для:

* HRV
* RHR
* сон
* шаги

Тогда можно говорить:

> HRV на 18% ниже вашей нормы

а не

> HRV = 42

---

# Что выглядит как потенциальный killer feature

Не чат.

Не OCR.

Не Telegram.

А именно сочетание:

```text
Apple Health
+
Дневник препаратов
+
Анализы
+
Исследования
```

Большинство health-приложений умеют максимум первые два пункта.

Если Tonus действительно сможет отвечать на вопросы вроде:

> После начала финастерида изменились ли сон, HRV или пульс?

или

> Есть ли связь между кофе после 15:00 и моим REM-сном?

то это уже уровень персонального health analyst, а не просто ещё одного трекера.

С точки зрения архитектуры я бы оценил текущую спецификацию примерно на **8.5/10 для MVP**. Основные недостающие элементы — единый слой контекста ИИ, система фоновых задач, версионирование промптов и вычисляемые health scores. После их добавления спецификация будет выглядеть как полноценный production-ready план.
