# Tonus — дизайн: закрыть дыры в AI-контексте чата (умнее и честнее ответы)

## 0. Цель

ИИ-чат (`chat-health`, использует общий билдер `_shared/healthContext.ts`) даёт
слабые или недостоверные ответы там, где данные либо есть в БД, но не попадают
в контекст, либо контекст недостаточно детализирован для честного ответа, либо
модель физически не может ни доуточнить, ни как следует обдумать вопрос.
Конкретный триггер: пользователь спросил «сравни эту неделю и прошлую по
времени засыпания» — ИИ сначала правдиво ответил «нет данных о времени
засыпания» (потому что действительно не видит `bedtime`), но чуть раньше в том
же диалоге дал сравнение «эта неделя vs прошлая» по часам сна с конкретными
цифрами (7.4ч vs 7.2ч), хотя контекст не содержит разбивки на две недели —
это, скорее всего, придуманные моделью числа, а не честный расчёт.

Дизайн закрывает это по трём направлениям: (1) данные, которые есть в БД, но
не долетают до модели, (2) агрегаты, которых не хватает для честных сравнений
без выдумывания, (3) архитектурные ограничения самого вызова (модель не может
доуточнить/дозапросить, расширенное мышление выключено, память диалога короткая).

## 1. Контекст (как сейчас устроено)

- Единый билдер контекста для чата/бота/отчётов:
  [supabase/functions/_shared/healthContext.ts](../../../supabase/functions/_shared/healthContext.ts)
  — `buildHealthContext()` (сборка данных) + `healthContextToText()` (рендер в
  текст промпта).
- Используется в [supabase/functions/chat-health/index.ts](../../../supabase/functions/chat-health/index.ts)
  с окном `periodDays: 30`. Модель — Gemini 2.5 Flash, `thinkingBudget: 0`,
  без function-calling — весь контекст статично вставляется в промпт один раз
  за запрос, `MAX_HISTORY = 6` последних сообщений диалога.
- Тесты билдера: [supabase/functions/_shared/healthContext.test.ts](../../../supabase/functions/_shared/healthContext.test.ts)
  — паттерн: тест на попадание секции в `buildHealthContext()` + тест на рендер
  текста + тест «full coverage» (все секции сразу) + тест «omits when empty».
  Новые секции должны следовать этому же паттерну.
- Системный промпт прямо запрещает выдумывать данные («Не выдумывай данные,
  которых нет в контексте») — значит пробелы в контексте нужно закрывать
  данными, а не полагаться на то, что модель домыслит корректно.
- Cost guard: `checkBudget()` проверяется один раз перед вызовом Gemini;
  `ai_usage` логирует `tokens_used` одной записью на чат-запрос.

## 2. Решения (зафиксированы)

Семь независимых доработок, каждая — свой раздел ниже:
3) время засыпания/пробуждения, 4) честные недельные сравнения, 5) health
concerns + hair entries, 6) health_alerts (страж здоровья), 7) recommendations
(история прошлых советов), 8) goal_progress (тренд к цели), 9) tool-use
(агентный доступ к точным диапазонам), 10) thinkingBudget + глубина истории.

Осознанно **не входит** в этот заход: сырые `heart_rate_samples` — см. раздел 11.

## 3. Время засыпания и пробуждения

- `sleep_sessions` уже хранит `bedtime`/`wake_time` (timestamptz, пишет
  `ingest-health` из Apple Health), но запрос в `buildHealthContext()`
  (строки 49-51) их не выбирает.
- **Изменение в `buildHealthContext()`:** добавить `bedtime, wake_time` в
  select `sleep_sessions`.
- **Часовой пояс:** добавить в `HealthContextOptions` необязательное поле
  `timezone` (по умолчанию `'Europe/Berlin'`, как дефолт в `profiles.timezone`);
  вызывающая функция (`chat-health/index.ts`) подтягивает `profiles.timezone`
  пользователя и передаёт его в `buildHealthContext`. Не хардкодим таймзону,
  как это сделано в `biweekly-report` (существующий баг там не трогаем).
- **Рендер:** в блоке «Последние ночи» (сейчас строки 151-154) добавить время
  засыпания/пробуждения в формате `HH:MM` по местному времени:
  `2026-07-05: заснул 23:47, встал 07:10, всего 7.2ч (глуб 1.1, REM 1.7)`.
  Если `bedtime`/`wake_time` для конкретной ночи `null` — просто не показывать
  время для этой строки (не писать «—», чтобы не засорять текст).
- **Средняя цифра:** добавить сводную строку по аналогии с другими метриками,
  например `Среднее время засыпания: 23:52`. Считать среднее по времени суток
  нужно с учётом перехода через полночь (см. уже существующий `avgTime()` в
  `supplement-schedule/index.ts` — переиспользовать ту же идею «wrap», но
  реализовать локально в `healthContext.ts`, т.к. `_shared` не должен тянуть
  зависимость на другую edge-функцию).

## 4. Честные недельные сравнения (последние 7 дней vs предыдущие 7 дней)

- Сейчас `healthContextToText()` даёт только: (а) одно среднее по всему окну
  `periodDays` (30 дней) и (б) сырые данные по последним 5 дням (`metrics`) /
  7 ночам (`sleep`). Разбивки на «эта неделя» / «прошлая неделя» нет вообще —
  если пользователь просит такое сравнение, модели физически не на что
  опереться кроме как оценить/придумать.
- **Изменение:** в `healthContextToText()` для `ctx.metrics` и `ctx.sleep`
  посчитать и явно вывести два блока агрегатов при условии, что в данных
  хватает дней (полных 7+7): `Последние 7 дней` и `Предыдущие 7 дней` — с теми
  же метриками, что уже агрегируются за весь период (RHR, HRV, сон, шаги,
  активные ккал, SpO2 для `metrics`; глубокий/REM/лёгкий сон для `sleep`), плюс
  среднее время засыпания из п.3.
- Если данных за 14 дней не хватает (пользователь недавно начал синхронизацию),
  блок «Предыдущие 7 дней» просто не рендерится (как и остальные секции —
  паттерн «omit when empty/insufficient» уже используется в файле). Порог:
  нужно минимум 14 записей в массиве (`ctx.metrics.length >= 14` /
  `ctx.sleep.length >= 14`), иначе блок «Предыдущие 7 дней» опускается, а
  «Последние 7 дней» рендерится, если записей хватает хотя бы на 7.
- Важно порядок сортировки: `ctx.metrics` отсортирован по возрастанию даты
  (строка 48, старые→новые) — «последние 7» это `slice(-7)`, «предыдущие 7» —
  `slice(-14, -7)`. `ctx.sleep` отсортирован по убыванию (строка 51,
  новые→старые) — «последние 7» это `slice(0, 7)`, «предыдущие 7» —
  `slice(7, 14)`. Не перепутать направления при реализации.
- Эта доработка не трогает `buildHealthContext()` (никаких новых полей из БД —
  только пересчёт из уже загруженных `ctx.metrics`/`ctx.sleep`), меняется
  только `healthContextToText()`.

## 5. Health concerns + hair entries (самоотчёты о симптомах)

- Таблицы `health_concerns` (name, category, status, started_at, notes) и
  `concern_logs` (date, severity 1-5, note) сейчас вообще не запрашиваются в
  `buildHealthContext()` — если пользователь ведёт трекинг симптома
  (кожа/волосы/дыхание/жкт), ИИ о нём не знает и не может связать с данными
  сна/HRV/окружения.
- `hair_entries` (ежемесячные замеры: shedding_level, density_rating,
  hairline_rating, scalp_note 1-5) — количественный трекинг волос, логично
  подмешать туда же, где concern с `category = 'hair'`. Фото-поля
  (`photo_top`/`photo_hairline`/`photo_temples`) в текстовый контекст не идут.
- **Изменение в `buildHealthContext()`:** добавить в `Promise.all`:
  - `health_concerns` где `status in ('active', 'improving')`, лимит 10;
  - `concern_logs` за `periodDays`, отсортировано по дате, лимит 30;
  - `hair_entries` за `periodDays`, отсортировано по дате, лимит 6 (замеры
    ежемесячные, 6 записей = полгода истории).
- **Новые поля контекста:** `concerns: { name, category, status, logs: { date,
  severity, note }[] }[]` (группировка логов по `concern_id` на стороне JS, как
  уже сделано для `supplementLogs` с `supplements(name)`) и `hairEntries: {
  date, shedding_level, density_rating, hairline_rating, scalp_note }[]`.
- **Рендер:** новый блок в `healthContextToText()`, аналогично блоку «Заметки
  дня»:
  ```
  Отслеживаемые симптомы:
  — Высыпания (кожа, active): последняя severity 3/5 (2026-07-04, "после кофе хуже")
  — Выпадение волос (hair, active): последняя severity 2/5 (2026-06-28)
    Замеры волос: 2026-06-15 — выпадение 2/5, густота 3/5, линия роста 4/5
  ```
  Показываем только последний лог/замер на concern (не весь список — глубже
  история не нужна для чата, это уже отдельная задача).

## 6. Health alerts — страж здоровья (проактивные аномалии)

- Изначально я по ошибке счёл `health_alerts` внутренним dedup-стейтом
  напоминаний (так было в устаревшем `schema.sql`). После миграции
  [20260705220000_health_alerts_anomaly.sql](../../../supabase/migrations/20260705220000_health_alerts_anomaly.sql)
  строки с `type = 'anomaly'` содержат полноценные данные детектора аномалий
  (`ingest-health/index.ts:216-260`): `level` (`yellow`/`red`), `findings`
  (jsonb), `message` (готовый текст алерта), `date`. Это ровно то, что
  системный промпт просит учитывать («если есть тревожные значения — мягко
  порекомендуй врача»), а ИИ сейчас об этом не знает.
- Легаси-строки (`type` вроде `hair_photo_reminder`, `labs_outdated_reminder`,
  без `level`/`message`) — это дедуп-стейт напоминаний, не контент; их
  фильтруем.
- **Изменение в `buildHealthContext()`:** запрос `health_alerts` где
  `type = 'anomaly'` и `level is not null`, за `periodDays`, лимит 5,
  сортировка по `created_at desc`.
- **Новое поле контекста:** `alerts: { date, level, message,
  acknowledged_at }[]`.
- **Рендер:**
  ```
  Алерты стража здоровья (⚠️ = red, требует внимания):
  — 2026-07-03 ⚠️ Резкий рост пульса покоя и падение HRV — возможна перегрузка/недосып
  ```
  Не подтверждённые (`acknowledged_at is null`) помечать отдельно не нужно —
  сам факт присутствия в списке уже сигнал, что стоит упомянуть в ответе.

## 7. Recommendations — история прошлых советов ИИ

- `recommendations` (metric, text, rationale, suggested_target, status:
  new/accepted/dismissed/snoozed, source) сейчас не видна модели. Риск: ИИ
  предлагает совет, который пользователь уже явно отклонил (`dismissed`), или
  не в курсе, что пользователь уже согласился с рекомендацией (`accepted`) —
  дублирует то, что уже стало практикой (или должно отражаться в целях/
  экспериментах, если конвертировано).
- **Изменение в `buildHealthContext()`:** запрос `recommendations` где
  `status in ('accepted', 'dismissed', 'snoozed')`, лимит 10, сортировка по
  `created_at desc`. Статус `new` не берём — это ещё непоказанные пользователю
  черновики, нерелевантны диалогу.
- **Новое поле контекста:** `recommendations: { metric, text, status,
  created_at }[]`.
- **Рендер:**
  ```
  Прошлые рекомендации ИИ (не повторяй отклонённые, учитывай принятые):
  — [dismissed] Ложиться на 30 мин раньше (метрика sleepHours)
  — [accepted] Магний 400мг перед сном (метрика hrv)
  ```

## 8. Goal progress — реальный тренд к цели

- Сейчас `ctx.goals` показывает только статичные `baseline_value`/
  `target_value`/`status` из таблицы `goals` — нет фактического движения к
  цели по дням. `goal_progress` (date, value, on_target) даёт этот тренд, но
  не запрашивается.
- **Изменение в `buildHealthContext()`:** для каждой активной цели —
  `goal_progress` за последние 7 дней, отсортировано по дате. Проще всего:
  один запрос `goal_progress` с `goal_id in (...)` (id активных целей) и
  `date >= sinceStr7`, группировка по `goal_id` на стороне JS.
- **Новое поле контекста:** дополнить существующие элементы `ctx.goals`
  необязательным `recentProgress: { date, value, on_target }[]`.
- **Рендер:** дополнить существующую строку цели, а не добавлять новый блок:
  ```
  — Сон 8ч: повысить sleepHours до 8 (старт 6.8), срок до 2026-08-01
    Последние 7 дней: 7.1, 7.3, 7.0, 7.4, 7.2, 7.5, 7.6 (на цели: 3/7 дней)
  ```

## 9. Tool-use — агентный доступ к точным диапазонам данных

Самая крупная часть. Базовый контекст (30 дней + недельные агрегаты из
раздела 4) покрывает большинство вопросов бесплатно и без доп. задержки. Но
для двух классов вопросов его принципиально недостаточно:
(а) данные старше 30 дней («сравни с маем»), (б) произвольные несовпадающие с
недельной сеткой диапазоны или полная история одного лабораторного маркера
(сейчас видно только последнее значение + дельта к предыдущему).

### 9.1 Определяемые инструменты (Gemini function calling)

Три функции, регистрируются в `tools: [{ functionDeclarations: [...] }]`
запроса к Gemini:

1. `get_metrics_range(start_date, end_date)` → сырые `daily_metrics`-строки
   (`resting_heart_rate, hrv, sleep_hours, steps, active_energy,
   oxygen_saturation`) за произвольный диапазон. Максимум 60 дней за один
   вызов (защита от раздувания токенов и цены).
2. `get_sleep_range(start_date, end_date)` → сырые `sleep_sessions`-строки
   (включая `bedtime`/`wake_time`) за произвольный диапазон, тот же лимит 60
   дней.
3. `get_lab_history(marker)` → вся история значений `lab_results` по
   конкретному маркеру (не только последнее + дельта), лимит 50 точек.
4. `get_correlations(outcome?)` → реальные лаг-корреляции (Пирсон, факторы:
   кофе/алкоголь/физактивность/шаги/время засыпания/погода → сон/HRV/пульс/
   готовность), опционально отфильтрованные по исходу. Закрывает конкретный
   провал из примера в разделе 0 — вопрос «с чем связано» сейчас отвечается
   догадкой модели, хотя в проекте **уже есть** готовый детерминированный
   движок корреляций ([src/lib/correlations.ts](../../../src/lib/correlations.ts),
   F3 smart-tonus), просто не подключённый к чату — используется только в
   отдельном виджете `CorrelationsBlock.tsx` и в фиче `deep-research`. Логику
   (`computeLagCorrelations`, чистая математика, без Deno/браузер-специфики)
   нужно портировать в `_shared/correlations.ts` — дублирование между
   `src/lib` и `_shared` уже есть как паттерн в проекте (`scores.ts`).
   Исполнитель инструмента сам собирает вход (30 дней `daily_metrics` +
   `sleep_sessions.bedtime` + `metrics_daily` где `metric='exerciseMinutes'`
   + `daily_scores.readiness` за диапазон + `intake_events` coffee/alcohol +
   `environment_daily`) и вызывает порт `computeLagCorrelations`.

Каждая функция выполняется как обычный Supabase-запрос с `eq('user_id',
user.id)` — те же RLS-гарантии, что и у остального контекста; модель не может
запросить чужие данные, только даты/маркер/исход как параметры.

### 9.2 Цикл вызова (chat-health/index.ts)

- Текущий одиночный `fetch` к `generateContent` оборачивается в цикл с
  жёстким потолком **2 дополнительных раунда** (итого максимум 3 вызова
  Gemini на одно сообщение пользователя — предохранитель от цены/задержки).
- После каждого ответа проверяем `candidates[0].content.parts` на
  `functionCall`. Если есть — выполняем соответствующий запрос к БД,
  добавляем в `contents` пару `{role:'model', parts:[functionCall]}` +
  `{role:'function', parts:[{functionResponse:{name, response}}]}`, повторяем
  запрос к Gemini.
- Если функция вызвана с недопустимыми параметрами (например, диапазон >60
  дней) — возвращаем `functionResponse` с ошибкой-как-текстом (не бросаем
  исключение), модель должна сама сузить диапазон или ответить на основе
  того, что есть.
- По достижении потолка раундов — финальный вызов без `tools` в запросе,
  чтобы модель была вынуждена дать текстовый ответ на основе того, что уже
  получила.
- **Учёт токенов:** `tokensUsed` суммируется по всем раундам цикла (сейчас
  берётся из единственного ответа) — иначе `ai_usage`/cost guard будут
  недосчитывать реальный расход при использовании инструментов.

### 9.3 Что не меняется

- `checkBudget()` перед стартом цикла остаётся одноразовой проверкой (как
  сейчас) — не проверяем бюджет между раундами, цикл короткий (макс. 3
  вызова) и это предохранитель, а не бухгалтерия в реальном времени.
- Базовый контекст (`healthContextToText`) продолжает передаваться в первом
  сообщении целиком, как сейчас — инструменты дополняют его, а не заменяют.

## 10. thinkingBudget и глубина истории

- `thinkingConfig: { thinkingBudget: 0 }` → `{ thinkingBudget: 1024 }` в
  [chat-health/index.ts:118](../../../supabase/functions/chat-health/index.ts).
  Небольшой фиксированный бюджет вместо 0 или неограниченного/динамического —
  ответы чуть медленнее и чуть дороже, но без риска непредсказуемого скачка
  цены. `maxOutputTokens` не трогаем (600 хватает на видимый ответ, thinking-
  токены считаются отдельно и не идут в `parts[0].text`).
- `MAX_HISTORY = 6` → `12` — глубже память диалога для многоходовых уточнений
  (пример из тикета — как раз 4+ реплики подряд про один и тот же срез
  данных). Простая константа, без побочных эффектов на остальной пайплайн.

## 11. Вне контекста этого дизайна

**`heart_rate_samples`** — сырые почти поминутные точки пульса
(`schema.sql:104-113`, "for stress map"), за день может быть 1000+ строк.
Текстовое включение в промпт нецелесообразно по токенам/цене — модель и так
получает пульс в переваренном виде через `daily_metrics`
(`resting_heart_rate`/`hrv`). Это не пробел, а осознанное архитектурное
решение: разным типам данных — разный способ попадания к модели (агрегат в
контексте vs, при необходимости позже, отдельный tool с агрегацией на лету, а
не сырой дамп).
