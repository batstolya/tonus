# Дизайн: «Что важнее всего» (рычаги) + самочувствие 1–5

Дата: 2026-06-21
Статус: утверждён, готов к плану реализации
Ветка: `feat/environment-correlations` (будет своя feature-ветка под реализацию)

## Зачем

Движок исследований (`src/lib/research.ts`) уже находит закономерности (корреляции
Пирсона + эффект событий через Cohen's d) и помечает среду как немодифицируемый
фактор. Но у продукта две дыры, обе названы во внешнем ревью:

1. **Нет субъективного исхода.** Всё крутится вокруг объективных метрик (HRV, сон).
   Человека же интересует «как я себя чувствую». Без этого исхода эксперименты и
   корреляции отвечают не на тот вопрос.
2. **Список корреляций не отвечает «и что теперь?».** Пользователь видит плоский
   список находок, но не видит, **что из этого важнее всего** и **насколько можно
   доверять** выводу.

Эта работа закрывает обе дыры одним связным срезом: собрать недостающий
субъективный outcome (самочувствие 1–5) и на его основе (плюс сон/HRV/готовность)
показывать **ранжированные, помеченные уверенностью рычаги** — управляемые
привычки, которые сильнее всего влияют на состояние.

Ключевой принцип удешевления: ранжирование рычагов — это **слой поверх уже
считающегося** `computeFindings`, а не новая математика. `Finding` уже несёт
`strength` (нормированная сила), `n`, `direction`, `deltaPct`, `modifiable`.

## Не-цели (вне этой спеки)

- **Время засыпания / латентность сна** — фаза 2. Сначала нужен спайк: отдаёт ли
  Apple Health латентность или её надо выводить из «лёг vs уснул».
- **Ввод самочувствия в вебе** — пока только Telegram. Веб только читает значение.
- **Строгая статистика (p-values / доверительные интервалы)** — вводим только если
  эвристический `confidence` окажется недостаточным на практике.
- Рефакторинг существующих экранов сверх того, что нужно для топ-блока.

## Часть 1. Самочувствие 1–5 (новый исход)

### Сбор — вечерний вопрос в Telegram

Сейчас вечерний вопрос (`telegram-bot/index.ts`, ветка `awaiting_note_date`)
ставит флаг ожидания и кладёт свободный текст ответа в `context_notes.note`.

Расширяем: сообщение вечернего вопроса получает инлайн-клавиатуру с кнопками
`1 2 3 4 5` (плюс короткие подписи-эмодзи опционально). Два **независимых,
опциональных** пути ввода:

- **Тап по кнопке** → `callback_query` с `callback_data = "wb:<YYYY-MM-DD>:<score>"`.
  Обработчик callback пишет `wellbeing` в `context_notes` за указанную дату
  (upsert по `(user_id, date)`), отвечает подтверждением и убирает клавиатуру.
  Дата берётся из payload, а не из текущего момента (вопрос может прийти близко к
  полуночи).
- **Свободный текст** → как сейчас, дополняет `context_notes.note`. Не требует
  предварительного тапа и не сбрасывается тапом.

Edge-кейсы:
- Можно поставить оценку без текста и текст без оценки.
- Повторный тап за тот же день — перезаписывает `wellbeing` (последнее значение).
- `awaiting_note_date` остаётся механизмом для текста; callback самодостаточен и не
  зависит от флага (несёт дату в себе).

### Хранение

Миграция: `ALTER TABLE context_notes ADD COLUMN wellbeing smallint`
(nullable, без дефолта; допустимый диапазон 1–5 — валидация на стороне бота/клиента,
жёсткий CHECK опционален). Существующий ключ `(user_id, date)` переиспользуется.

`src/lib/contextNotes.ts` дополняем: `loadRecentNotes` и связанные селекты тянут
`wellbeing`; добавляем хелпер чтения серии самочувствия по дням (для движка).

### Куда течёт

- **`research.ts`** — самочувствие становится новой непрерывной метрикой-исходом
  (см. Часть 2).
- **`healthContext.ts`** — самочувствие за период попадает в контекст ИИ-чата
  (ИИ видит субъективное состояние наряду со сном/HRV).

## Часть 2. Движок рычагов

### Что такое «рычаг»

Рычаг = эффект **управляемого поведения** на **исход**. Это подмножество уже
вычисленных `Finding` вида `kind: 'event'`, где событие — управляемая привычка, а
цель — outcome-метрика. Метрика↔метрика и корреляции проблем рычагами не являются
(это не поведение) и в рычаги не попадают.

### Исходы (outcomes)

Ранжируем рычаги против четырёх исходов:

| Исход | Источник |
|---|---|
| Самочувствие 1–5 | `context_notes.wellbeing` (новое) |
| Сон (длительность) | `daily_metrics.sleepHours` (есть) |
| HRV | `daily_metrics.hrv` (есть) |
| Готовность | per-day, переиспользуя формулу `src/lib/scores.ts` (HRV·40 + RHR·30 + сон·30 относительно личной нормы) |

Самочувствие и готовность добавляются как новые колонки-исходы в строки
`ResearchData` (`loadResearchData`). Самочувствие — ординальная 1–5, трактуем как
непрерывную (`betterHigh: true`). Готовность — числовой композит 0–100,
вычисляется в пайплайне исследований per-day тем же кодом, что и на дашборде.

### Управляемость (controllability)

Вес фактора, множитель в скоре:

| Вес | Факторы |
|---|---|
| `1.0` | кофе, алкоголь, поздняя еда (после 21:00), тренировка, приём препарата (`sup_*`) |
| `0.5` | стресс (влияет косвенно) |
| `0.0` (исключены из рычагов) | среда (`env_*`), болезнь, поездка, любые метрика↔метрика и проблема-корреляции |

Факторы с весом `0` в список рычагов не попадают. Среда показывается **отдельно**
как 🌍 «неуправляемый контекст» (это уже помеченные `modifiable: false` находки).

### Скоринг

Для каждой пары *(управляемый фактор × исход)* из `Finding`:

```
score = impact × confidence × controllability
```

- **impact** — нормированная сила в [0,1]:
  - событие: `min(strength / 1.5, 1)` (где `strength` ≈ Cohen's d)
  - корреляция: `|r|` (уже 0–1)
- **confidence** ∈ [0,1]:
  ```
  confidence = 0.6 · clamp(n / 28, 0, 1)
             + 0.4 · clamp((strength − thr) / (strong − thr), 0, 1)
  ```
  где `thr` — порог появления находки (0.5 для d, 0.3 для |r|), `strong` —
  «уверенно сильный» (1.0 для d, 0.6 для |r|).
- **controllability** — вес из таблицы выше.

Бейдж уверенности из `confidence`:

| Бейдж | Условие |
|---|---|
| 🟢 высокая | `confidence ≥ 0.66` |
| 🟡 средняя | `0.33 ≤ confidence < 0.66` |
| 🔴 мало данных | `confidence < 0.33` |

### Модуль

Новый `src/lib/levers.ts`:

```ts
export interface Lever {
  factorLabel: string        // «Поздний кофе»
  outcomeLabel: string       // «Засыпание» / «HRV» / «Самочувствие»
  direction: 'pos' | 'neg'
  impactText: string         // «+38 мин» / «−22%»  (человекочитаемо из delta/deltaPct)
  score: number
  confidence: number
  badge: 'high' | 'medium' | 'low'
  controllability: number
  finding: Finding           // ссылка на исходную находку (для drill-down / эксперимента)
}

// Берёт результат computeFindings + ResearchData, возвращает топ рычагов и
// отдельно — немодифицируемый контекст (env-находки).
export function computeLevers(findings: Finding[], data: ResearchData): {
  levers: Lever[]            // топ-5, отсортированы по score desc
  context: Finding[]         // 🌍 немодифицируемые (modifiable === false)
}
```

`impactText` строится из существующих полей находки: для событий — `delta`
в единицах метрики (мин/мс) или `deltaPct` (%), для корреляций — словесно.

### Изменения в `research.ts`

- `loadResearchData`: добавить запрос самочувствия (`context_notes.wellbeing`) и
  per-day готовности; добавить обе как метрики-исходы в `METRICS`/строки.
- Существующий список событий и `computeFindings` не меняются по сути — самочувствие
  и готовность просто становятся новыми целями в `targets`, и движок автоматически
  посчитает по ним эффекты событий и корреляции.

## Часть 3. UI — топ-секция экрана «Исследования»

Тот же экран (`src/components/research/ResearchScreen.tsx`), тот же вызов
`computeFindings`, два представления:

1. **Сверху — «Что важнее всего»**: 3–5 карточек рычагов. Каждая карточка:
   - человекочитаемый эффект: «Поздний кофе → +38 мин к засыпанию», «Алкоголь → −22% HRV»
   - исход, на который влияет
   - бейдж уверенности 🟢 / 🟡 / 🔴
   - кнопка **«Проверить экспериментом»** → переход в создание n=1 с предзаполненной
     гипотезой (фактор + исход).
2. **Ниже — полный список находок** как drill-down (существующий рендер, без
   изменений по структуре).
3. Бейджи 🟢🟡🔴 проставляются и на старые карточки находок (хелпер из `levers.ts`
   переиспользуется) — бесплатный побочный выигрыш.

Если рычагов нет (мало данных) — блок показывает честный пустой статус
(«пока недостаточно данных, чтобы выделить рычаги») и не выдумывает.

## Часть 4. Привязка к экспериментам

Пункт 4 ревью («автоматический рейтинг гипотез») — это **тот же скоринг рычагов**,
отдельной формулы не вводим:

- Кнопка «Проверить экспериментом» на карточке рычага открывает
  `ExperimentsScreen` с предзаполненной гипотезой (что меняем = фактор, за чем
  следим = исход).
- Подсказки экспериментов (`suggest-experiments` / `ExperimentsScreen`)
  упорядочиваются по `score` рычагов: первыми предлагаются самые высокоэффективные
  и управляемые гипотезы.

Минимальная реализация фазы 1: порядок подсказок по score + предзаполнение гипотезы
из рычага. Глубокая переработка `suggest-experiments` — не требуется.

## Тестирование

- **Движок (`levers.ts`)** — юнит-тесты на синтетических `Finding[]`: фильтр по
  управляемости, формула score, границы бейджей (🟢/🟡/🔴), исключение среды,
  сортировка, пустой результат.
- **`research.ts`** — самочувствие и готовность реально появляются как исходы и по
  ним считаются эффекты (тест на синтетических днях).
- **Бот** — callback `wb:<date>:<score>` пишет корректную дату/значение; текст и
  оценка не мешают друг другу; повторный тап перезаписывает.
- **UI** — ручная проверка: топ-блок рендерит рычаги с правильными бейджами;
  пустой статус при нехватке данных; «Проверить экспериментом» уводит в n=1 с
  предзаполнением.
