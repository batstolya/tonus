# Программа снижения техдолга — дизайн

- **Дата:** 2026-07-13
- **Статус:** проектирование
- **Амбиция:** прагматично снизить риск (не полировать до нуля)

## Проблема

Аудит кодовой базы (~31k строк: ~21.6k фронтенд + ~9.4k edge-функций,
446 тестов, работающий CI/CD) выявил четыре независимые задолженности:

1. **Lint-долг и дырявая типизация.** 292 lint-ошибки зафиксированы «потолком»
   в CI (`MAX_LINT_ERRORS`), в основном `no-explicit-any` и unused vars.
   Отдельно **48 `any` в клиенте** (`src/`) — часть из них вокруг данных
   БД/сети, где `any` может дать реальный рантайм-баг, а не просто раздражать
   линтер.
2. **UI-слой почти не покрыт тестами по существу.** Окружение vitest — `node`,
   React не рендерится, поэтому тесты компонентов сведены к «проверка экспорта +
   покрытие переводов». Логику ветвления в компонентах ловят только
   playwright-смоуки.
3. **Крупные файлы-комки.** `translations.ts` (1063), `SettingsScreen.tsx`
   (854), `Dashboard.tsx` (471) — тяжело читать, менять и тестировать.
   (`database.types.ts` (2087) сгенерирован — не в счёт.)
4. **Ручное дублирование scores-логики.** Формулы живут в `src/lib/scores.ts`
   и вручную зеркалятся в `supabase/functions/_shared/scores.ts`; расхождение
   ловится golden-тестами. Работает, но синхронизация — ручная и хрупкая.

## Цель и не-цели

**Цель:** снизить риск и стоимость сопровождения по всем четырём долгам,
двигаясь прагматично — сначала то, что реально может сломаться в рантайме,
косметику потом. И, что важнее, **остановить рост долга**.

**Не-цели:**
- Не гонимся за 0 lint-ошибок и строгим глобальным баном `any`.
- Не переписываем архитектуру, не трогаем продуктовое поведение.
- Не рефакторим то, что не входит в четыре долга выше.

## Подход

Один спек — **программа**, а не одна фича. Она:

1. **Ставит забор** (Секция 1): долг перестаёт расти. Это дёшево и даёт эффект
   немедленно — чистить бессмысленно, пока в каждый PR может протекать новый
   `any`.
2. **Разбивает работу на 4 воркстрима** (Секция 2) с чёткими критериями
   готовности. Каждый воркстрим идёт **своим планом и своим PR** — они
   независимы и не должны блокировать друг друга.
3. **Меряет успех прагматичными планками** (Секция 3), а не абсолютами.

Отвергнутые альтернативы:
- **4 отдельных спека** — потерялась бы общая политика «долг не растёт»,
  а это ядро ценности.
- **Один спек = один план на всё** — план на 40+ шагов, разваливается
  на исполнении.

---

## Секция 1 — Политика «долг не растёт» (фундамент, делается первой)

Забор ставим до любой чистки.

### 1.1 Храповик lint-потолка

`MAX_LINT_ERRORS` в `.github/workflows/*.yml` **только уменьшается**.
Формализуем как правило проекта (уже есть механизм и комментарий в workflow):
любой PR, чинящий lint-ошибки, **обязан** снизить `MAX_LINT_ERRORS` до нового
фактического числа. CI уже падает при превышении — правило закрепляет движение
только вниз.

### 1.2 Запрет нового `any` в изменённом коде

Старые 48 `any` остаются под потолком; **новый `any` не проходит CI**.

Механизм:
- Включить `@typescript-eslint/no-explicit-any` как **warning** глобально
  (не ошибка — иначе потолок сломается).
- В CI добавить шаг, проверяющий **только изменённые строки** относительно
  базовой ветки: `eslint` по diff с `--max-warnings 0`. Новый `any` или новая
  ошибка на тронутых строках роняет CI.
- **pre-commit хук — опционально**, по решению на этапе плана; базовый гейт —
  CI (единственный обязательный барьер).

**Критерий готовности С1:** после мержа невозможно добавить `any` или
lint-ошибку в изменённом коде, не уронив CI; `MAX_LINT_ERRORS` может только
снижаться.

## Секция 2 — Воркстримы (каждый = отдельный план/PR)

### Воркстрим A — Типизация клиента (`any` → типы), по риску

48 `any` не равны. Делим по риску:

- **A1 (высокий риск, первым):** `any` вокруг данных БД и сетевых ответов.
  Здесь неверный тип = рантайм-баг. Опираемся на сгенерированный
  `src/lib/database.types.ts` — заменяем `any` конкретными Row/Insert-типами.
- **A2 (косметика, вторым):** `any` в recharts, утилях, обработчиках событий.
  Заменяем на точные типы или узкие дженерики; где библиотека реально не даёт
  типа — `unknown` + сужение, не `any`.

Каждая пачка снижает `MAX_LINT_ERRORS` (Секция 1.1).

**Критерий:** 0 `any` в модулях, работающих с БД/сетью; остальные `any`
снижены значимо и учтены в потолке.

### Воркстрим B — Тесты UI-слоя

Инфраструктура (делается до A, чтобы рефакторинг A/C был под защитой тестов):

- Добавить **jsdom-проект в vitest** через `test.projects` — отдельный проект
  с `environment: 'jsdom'`, чтобы существующие node-тесты чистой логики
  **не трогать** (они остаются в node-окружении и работают как раньше).
- Подключить `@testing-library/react` (+ `@testing-library/jest-dom`).
- Покрыть **сначала компоненты с логикой ветвления** (Dashboard,
  SettingsScreen и топ по сложности), а не «экспорт + переводы».
- Playwright остаётся для сквозных сценариев — jsdom его не заменяет.

**Критерий:** jsdom-проект настроен и зелёный; топ-5 компонентов по сложности
покрыты тестами реального поведения; node-тесты логики не сломаны.

### Воркстрим C — Декомпозиция крупных файлов

- `translations.ts` (1063) → разбить по фичам (напр. `translations/dashboard.ts`,
  `translations/settings.ts`), собрать в общий индекс. Покрытие переводов
  (существующие тесты) — страховка от потери ключей.
- `SettingsScreen.tsx` (854) → выделить секции в под-компоненты
  (`settings/<Section>.tsx`).
- `Dashboard.tsx` (471) → по желанию, если укладывается в бюджет.

**Критерий:** ни один **продуктовый** файл (кроме сгенерированного
`database.types.ts`) не превышает ~400 строк.

### Воркстрим D — Автогенерация scores-зеркала (последним)

Самый рискованный: формулы скорингов критичны для дашборда, коуча и
ИИ-контекста. Делаем **последним**, golden-тесты сохраняем как страховку.

- Единый источник формул + скрипт, который генерирует (или проверяет
  идентичность) второе зеркало.
- Вариант проверки (безопаснее переписывания): CI-шаг сравнивает, что
  `src/lib/scores.ts` и `_shared/scores.ts` дают идентичный результат на общем
  наборе входов — но окончательный механизм выбирается на этапе плана D.

**Критерий:** ручная синхронизация двух копий исключена; расхождение формул
невозможно смержить (ловится в CI автоматически).

### Порядок исполнения

```
Секция 1 (забор)
   └─> B (инфра тестов)   ← защищает последующий рефакторинг
        └─> A (типизация)
             └─> C (декомпозиция)
                  └─> D (scores-зеркало, самый рискованный — последним)
```

## Секция 3 — Критерии успеха программы

- **Lint-потолок** снижен с 292 до **<100** (прагматично, не 0).
- **0 `any`** в модулях клиента, работающих с БД/сетью.
- **Новый `any`/lint** в изменённом коде роняет CI (Секция 1.2).
- **jsdom-тесты** покрывают топ-5 компонентов по сложности.
- Ни один продуктовый файл **> ~400 строк** (кроме `database.types.ts`).
- **scores-зеркало** генерируется/проверяется автоматически, ручная
  синхронизация исключена.

Числовые планки (292→100, ~400 строк, топ-5) — целевые ориентиры прагматичной
амбиции; уточняются на этапе планов, если по ходу всплывут причины.

## Риски

- **A/C ломают поведение.** Митигация: воркстрим B (тесты) идёт раньше и
  покрывает рефакторимые компоненты; типизация A опирается на сгенерированные
  типы, а не на догадки.
- **D меняет критичные формулы.** Митигация: golden-тесты остаются; D
  предпочитает *проверку идентичности* переписыванию.
- **Забор (С1) тормозит обычную разработку.** Митигация: гейт бьёт только по
  изменённым строкам, легаси-долг остаётся под потолком, pre-commit —
  опционален.

## Тестирование

- Каждый воркстрим — зелёный CI (`npm test`, `npm run build`,
  playwright, lint-потолок) перед мержем.
- B добавляет новый пласт (jsdom) — проверяем, что node-проект логики
  не затронут.
- D сохраняет golden-тесты как обязательный барьер.
