# Умный Tonus: страж здоровья, единый AI-контекст, лаг-корреляции (+виджет, погода, соблюдение)

Дата: 2026-07-05 · Статус: дизайн утверждён · Реализация: F1–F3 сейчас, F4–F6 следом

## Зачем

Tonus собирает почасовые данные (RHR, HRV, температура запястья, дыхание, SpO₂),
но никак не реагирует на них между визитами пользователя. AI-коуч не знает целей
и экспериментов пользователя. Инсайты не видят отложенных эффектов (кофе сегодня →
HRV завтра). Эта спека закрывает три разрыва и добавляет три быстрые победы.

Решения пользователя (2026-07-05): алерты в два уровня; доставка Telegram + баннер
в приложении; корреляции показываем на экране Инсайты.

---

## F1. Страж здоровья — раннее предупреждение о болезни

**Идея:** организм сигналит о заболевании за 24–48 ч до симптомов: RHR↑,
температура запястья↑, HRV↓, частота дыхания↑, SpO₂↓. Все данные уже в
`metrics_daily` (EAV: `user_id, date, metric, avg_val…`).

### Детектор — `supabase/functions/_shared/anomaly.ts`

Чистый модуль без Deno-зависимостей (как `_shared/scores.ts`), с vitest-тестами.

- Вход: массив дней `{ date, rhr, wristTemp, hrv, respiratoryRate, spo2 }`
  (последние ~35 дней).
- База: среднее и стандартное отклонение по 30 дням **до** последних 2 дней
  (болезнь не должна загрязнять собственную базу). Минимум 10 дней истории,
  иначе детектор молчит.
- z-score последнего дня по каждой метрике, «плохое» направление:
  RHR `z ≥ +2`, температура `z ≥ +2`, дыхание `z ≥ +2`, HRV `z ≤ −2`, SpO₂ `z ≤ −2`.
- Уровни:
  - `yellow` — ровно одна метрика пересекла порог |z| ≥ 2;
  - `red` — две и более метрик с |z| ≥ 1.5 в плохую сторону.
- Выход: `null` либо `{ level, findings: [{ metric, value, baseline, z }] }`.

### Запуск — внутри `ingest-health`

После записи метрик и скоров. Обёрнуто в try/catch: ошибка детектора логируется
и **не валит инжест**. Отдельный cron не нужен — HAE шлёт данные каждый час.

### Хранение — таблица `health_alerts` (миграция)

```sql
create table health_alerts (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  date date not null,
  level text not null check (level in ('yellow','red')),
  findings jsonb not null,          -- [{metric, value, baseline, z}]
  message text not null,            -- готовый текст (ru)
  acknowledged_at timestamptz,
  created_at timestamptz not null default now()
);
-- RLS: пользователь видит и обновляет (acknowledge) только свои
```

### Кулдаун и эскалация

Перед вставкой: если за последние 24 ч уже есть алерт этого уровня или выше —
пропустить. Жёлтый → красный проходит сразу (эскалация важнее тишины).

### Доставка

1. **Telegram** — сразу после вставки, по образцу `send-reminders`
   (`TG_TOKEN`, chat_id из связки аккаунта). Текст: уровень, метрики
   с отклонениями («Пульс покоя 62 против нормы 55, +2.1σ»), совет
   («день без нагрузок, больше воды»), дисклеймер «не диагноз».
2. **Баннер на дашборде** — компонент `HealthAlertBanner`: последний
   не-acknowledged алерт не старше 48 ч. Кнопка «Понятно» пишет
   `acknowledged_at`. Жёлтый/красный стиль. Строки через `t()` + coverage-тест.

### Тесты

- `anomaly.test.ts`: здоровая серия → null; RHR+temp растут → red; только
  HRV упал → yellow; больные дни не загрязняют базу; <10 дней → null.
- Кулдаун — юнит-тест на чистой функции решения (без БД).

### Деплой

Миграция `health_alerts` → `ingest-health` **с `--no-verify-jwt`**.

## F2. Единый AI-контекст + цели и эксперименты

**Проблема:** два дублирующих билдера контекста — `src/lib/chat.ts`
(`buildContextSnapshot`, клиент) и `_shared/healthContext.ts` (сервер,
telegram-bot). Они дрейфуют. Цели (`goals`) и эксперименты (`experiments`)
не попадают ни в один — AI советует вслепую.

### Дизайн

1. **`_shared/healthContext.ts` — единственный билдер.** Добавить секции:
   - `goals`: активные цели (название, целевое значение, прогресс);
   - `experiments`: активные и недавно завершённые (гипотеза, статус, период);
   - соответствующие блоки в `healthContextToText`.
2. **`chat-health` строит контекст сам** по user id из JWT
   (`buildHealthContext(supabase, userId)`), веб шлёт только
   `{ message, history }`. Клиентский `buildContextSnapshot` и его
   обвязка удаляются из `src/lib/chat.ts`.
3. **telegram-bot и biweekly-report** получают цели/эксперименты бесплатно —
   они уже используют `buildHealthContext`.

### Трейд-офы (приняты)

- Чат в демо-режиме остаётся пустым — как и сейчас (данные чата в Supabase).
- Первый ответ чата чуть медленнее (контекст строится на сервере) — приемлемо.

### Тесты

- `healthContext.test.ts`: дополнить кейсами goals/experiments (пустые,
  активные, завершённые).
- `chat.test.ts`: обновить под упрощённый клиент.

### Деплой

`chat-health`, `telegram-bot`, `biweekly-report` (все импортируют healthContext
или получают его текст).

## F3. Лаг-корреляции — «Связи в твоих данных»

**Идея:** отложенные эффекты (сегодняшний кофе → завтрашний HRV) не поймать
разовым AI-запросом. Считаем их детерминированно и показываем честно.

### Движок — `src/lib/correlations.ts`

Чистый модуль + тесты. Без AI.

- **Факторы** (день X): кофе (кол-во из `intake_events`), алкоголь, тренировки
  (`exerciseMinutes`), шаги, время отбоя (`sleepBedtime` → минуты после 22:00).
- **Исходы** (день X+lag, lag ∈ {0, 1}): сон (часы), HRV, RHR, readiness.
  Лаг 2 не берём сознательно: 5 факторов × 4 исхода × 3 лага = 60 сравнений —
  растёт риск ложных «связей»; добавим, если лаг 1 окажется полезным.
- Пирсон по парным дням, минимум **14 пар**; сила: |r| ≥ 0.5 и n ≥ 21 —
  «сильная», |r| ≥ 0.3 — «заметная», иначе не показываем.
- Выход: топ-5 по |r|: `{ factor, outcome, lag, r, n, direction }`.
- Данных мало → `{ needMoreDays: N }` для честного эмпти-стейта.

### UI — секция в `InsightsScreen`

Карточки: «☕ Кофе → 📉 HRV **на следующий день** · сильная связь · 32 дня».
Иконки направления, серые карточки для «заметных». Эмпти-стейт: «Нужно ещё
N дней данных». Работает в демо на фикстурах (там 90 дней — связи найдутся).
Все строки через `t()` + coverage-тест.

### Фаза 2 (после F2)

Текстовый блок топ-корреляций добавляется в `healthContextToText` — AI-коуч
вплетает связи в советы. Отдельной задачей, не в первой итерации.

## F4. iPhone-виджет readiness

**Идея:** readiness на домашнем экране без открытия браузера.

- **Edge-функция `widget-data`** (GET): по долгоживущему токену
  (переиспользовать механику `ingest_tokens` — отдельный scope/таблица
  `widget_tokens`, чтобы не расширять права инжест-токена). Ответ:
  `{ readiness, level, updatedAt, alert: {level} | null }` — последняя строка
  `daily_scores` + активный `health_alerts`.
- **Scriptable-скрипт** в `docs/guides/iphone-widget.md`: маленький/средний
  виджет, цвет по уровню readiness, бейдж алерта. Инструкция установки
  (Scriptable бесплатный, 5 минут).
- Деплой с `--no-verify-jwt` (авторизация — собственный токен, как ingest).

## F6. Соблюдение препаратов

Данные есть: `supplements` (active) + `supplement_logs` (taken by date).

- **Расчёт** — `src/lib/adherence.ts`: % дней с приёмом за 14/30 дней
  по каждому активному препарату + общий; серия («5 дней подряд»).
- **UI** — блок в экране Препараты: прогресс-бары по препаратам, общий %.
- **Отчёт бота** — строка в двухнедельный отчёт: «Магний 86% (↑), Омега 64% (↓)»
  (после F2 — данные уже в healthContext-пайплайне).

## Порядок реализации

1. **F1** — миграция + `_shared/anomaly.ts` + вызов в ingest-health + Telegram + баннер
2. **F2** — расширение healthContext + серверный контекст в chat-health + чистка клиента
3. **F3** — `correlations.ts` + секция в Инсайтах
4. F4 → F5 → F6 отдельными итерациями по этой спеке

Каждая фаза: тесты → `npm test` → деплой затронутых функций → проверка на проде.

## Не делаем (осознанно)

- Web-push/PWA-уведомления — Telegram уже решает доставку.
- ML/сложные модели для аномалий — z-score против личной базы понятен,
  объясним и тестируем.
- Мультитенант-доработки — продукт для одного пользователя.
