# Tonus — дизайн: границы безопасности интеграций

## Решение по scope (review 2026-07-10)

Статус: **делаем целиком, первой из трёх спек.** Факты подтверждены по коду:
`telegram-bot` читает `TELEGRAM_WEBHOOK_SECRET`, но нигде не сравнивает его с
заголовком; `coach-weekly` трактует отсутствие `Authorization` как cron для всех
пользователей (плюс авторизация по частичному совпадению service key);
в git отслеживается 374 файла `claude-monitor/browser-profile/`.

Корректировки относительно текста ниже:

- **§3.3 register-webhook: не защищаем, а удаляем из деплоя.** Регистрация
  webhook остаётся CLI-скриптом/runbook-командой. Меньше кода, на один секрет
  (`TONUS_ADMIN_SECRET`) меньше, сценарий редкий. Ответ на вопрос №3 из §8.
- **§4.2 переписывание git-истории: отложено.** Репозиторий приватный и не
  раздавался третьим лицам. Сейчас обязательны только ротация сессий из
  browser profile и `.gitignore` + `git rm --cached` (§4.1). History rewrite —
  отдельная операция, выполняется при первом расширении доступа к репо.
- Ответ на вопрос №1 из §8: один `TONUS_CRON_SECRET`, существующие cron
  secrets футбольных функций и `sync-cal` — временные алиасы при деплое.

## 0. Цель

Закрыть публичные пути, которые сейчас могут принять поддельный запрос и
выполнить действие от имени Tonus: изменить данные пользователя, отправить
сообщение в Telegram или потратить AI-бюджет. Одновременно убрать из git
браузерный профиль и исключить повторное появление runtime-данных в репозитории.

Результат: каждый endpoint с побочным эффектом имеет явный и обязательный
способ аутентификации, а репозиторий не хранит сессии, cookies, кэши или PID.

## 1. Контекст и подтверждённые риски

- `telegram-bot` развёрнут с `verify_jwt = false`. При регистрации Telegram
  получает `secret_token`, но handler читает тело запроса до проверки
  `X-Telegram-Bot-Api-Secret-Token`; переменная `WEBHOOK_SECRET` объявлена, но
  не используется.
- `send-reminders` также развёрнут без JWT и принимает любой HTTP-запрос.
  Этот запрос может отправить напоминания всем подходящим пользователям.
- `coach-weekly` трактует отсутствие `Authorization` как cron-вызов и запускает
  разбор для всех активных пользователей, включая Gemini-вызовы и Telegram.
- `register-webhook` публично вызывает Telegram Bot API с настоящим bot token.
- В git отслеживается `claude-monitor/browser-profile/`: Chromium cookies,
  storage, history, cache и runtime-файлы `monitor.pid` / `state.json`.

Это не просто hardening: данные пути являются P0 до следующего расширения
аудитории или открытия репозитория третьим лицам.

## 2. Принципы

1. **Fail closed.** Отсутствующий или пустой секрет не означает разрешённый
   вызов. Endpoint с side effect возвращает 401 и ничего не делает.
2. **Проверка до работы.** Сначала проверяются метод и credentials, только затем
   читается body, создаётся service-role client или вызывается Telegram/Gemini.
3. **Один тип доверия на роль.** Telegram доверяется только Telegram secret;
   cron — только cron secret; пользовательские вызовы — только валидному
   Supabase JWT; ручная админ-операция — только отдельному admin secret.
4. **Никаких секретов в SQL, README или git.** Планировщик получает секрет из
   защищённой runtime-конфигурации; значения не попадают в миграции и логи.
5. **Совместимость без небезопасного fallback.** Старый незащищённый путь не
   остаётся «временно» рабочим.

## 3. Целевая модель авторизации

### 3.1 Telegram webhook

`telegram-bot` принимает только `POST`. До `req.json()` он должен:

1. прочитать `TELEGRAM_WEBHOOK_SECRET`;
2. вернуть 503, если секрет не задан в runtime;
3. сравнить его с заголовком `X-Telegram-Bot-Api-Secret-Token`;
4. вернуть 401 при несовпадении;
5. только затем обработать Telegram Update.

В `register-webhook` остаётся `secret_token: TELEGRAM_WEBHOOK_SECRET`. После
деплоя нужно заново вызвать регистрацию webhook, иначе Telegram продолжит
присылать запросы без нового заголовка.

**Не допускается:** проверять только наличие заголовка, принимать пустой secret,
или проверять header после вызова `setupCommands()` / записи в БД.

### 3.2 Cron и внутренние планировщики

Вводится один обязательный runtime secret `TONUS_CRON_SECRET`. Общий Deno-helper
в `supabase/functions/_shared/` получает `Request` и возвращает успешный
результат либо 401. Он сравнивает `x-cron-secret` с `TONUS_CRON_SECRET` и
никогда не считает отсутствие `Authorization` доказательством доверия.

Этим helper пользуются:

- `send-reminders`;
- `coach-weekly` в массовом cron-режиме;
- будущие выделенные sender-функции из automation spec.

`sync-cal` и футбольные функции приводятся к этому же поведению. Их текущие
секреты могут быть временно алиасами при деплое, но конечная модель — один
понятный контракт заголовка `x-cron-secret` и один documented secret name.

`coach-weekly` разделяет пути явно:

- запрос с корректным cron secret и без `userId` — массовая cron-задача;
- запрос с пользовательским JWT — разбор только этого пользователя;
- любой иной запрос — 401.

Service-role вызовы между функциями не передают service key как произвольный
маркер в header. Они используют отдельный internal secret либо прямой общий
код. Это не позволяет превратить частичное совпадение ключа в API-контракт.

### 3.3 Ручная регистрация Telegram webhook

`register-webhook` не является пользовательской функцией. Она защищается
`TONUS_ADMIN_SECRET` в заголовке `x-admin-secret`, проверяемым до JSON body.
Её разрешено вызывать только из закрытой operational-команды/CI.

Ответ `action=info` возвращает только безопасный минимум: `url`,
`pending_update_count`, `last_error_date`, `last_error_message`. Полный ответ
Telegram API не возвращается публичному клиенту.

Вариант с удалением функции и регистрацией webhook только CLI-скриптом также
безопасен. Для первого этапа выбран защищённый endpoint: он сохраняет текущий
операционный сценарий, но убирает публичный доступ.

### 3.4 Token-in-URL endpoints

`ingest-health` и `widget-data` не входят в этот релиз полностью: они уже
имеют пользовательские bearer-токены. Но оба контракта фиксируют следующий
переход: header `x-ingest-token` / `Authorization` является предпочтительным,
а `?token=` остаётся только на ограниченный период совместимости. Логи и ответы
никогда не печатают токен.

## 4. Browser profile и история git

### 4.1 Что убрать из рабочего дерева

`claude-monitor/browser-profile/` не является исходным кодом. Монитор должен
создавать профиль в локальном runtime-каталоге, заданном переменной окружения
или volume Docker/launchd, но не внутри отслеживаемой части репозитория.

В `.gitignore` добавляются как минимум:

```gitignore
claude-monitor/browser-profile/
claude-monitor/data/*.pid
claude-monitor/data/state.json
```

В репозитории остаются только исходники монитора, пример конфигурации и
документация установки. Никакие реальные cookies, SQLite DB, browser cache,
PID или snapshots состояния не коммитятся.

### 4.2 Реакция на уже попавшие данные

Это отдельная административная операция, не автоматический commit:

1. владелец определяет, был ли репозиторий доступен вне доверенной группы;
2. ротируются сессии/токены, которые могли присутствовать в профиле;
3. выполняется backup и переписывается история через согласованный инструмент
   очистки git history;
4. выполняется force-push, участники заново клонируют репозиторий;
5. скан истории подтверждает отсутствие `browser-profile/`.

Нельзя ограничиться `git rm` в новом коммите: старые blobs останутся доступны
из истории.

## 5. Изменяемые границы

| Зона | Изменение | Не меняем |
|---|---|---|
| Telegram inbound | Проверка secret header до side effect | Команды и UX бота |
| Cron | Обязательный `x-cron-secret` | Расписание и продуктовые правила |
| Admin webhook | Изолированный admin secret | Список Telegram-команд |
| HAE / widget | Только контракт будущей миграции токена | Данные и формат виджета |
| Monitor | Runtime профиль вне git + игнор | Логику мониторинга Claude |

## 6. Проверка и acceptance criteria

### Автоматически

- unit-тесты helper’ов: missing, empty, wrong и correct secret;
- unit-тест `telegram-bot`: неверный Telegram header не вызывает
  `createClient`, `setupCommands` и Telegram API;
- тест `coach-weekly`: отсутствие Authorization без cron secret возвращает 401,
  JWT вызывает только своего пользователя, cron secret разрешает массовый путь;
- тест `send-reminders`: вызов без cron secret не читает таблицы;
- repository test: `git ls-files` не содержит `claude-monitor/browser-profile`,
  `*.pid` или `claude-monitor/data/state.json`.

### Перед релизом

- задать `TELEGRAM_WEBHOOK_SECRET`, `TONUS_CRON_SECRET`, `TONUS_ADMIN_SECRET`
  в Supabase secrets, не в Vercel env и не в SQL;
- задеплоить затронутые Edge Functions;
- заново зарегистрировать Telegram webhook защищённой операционной командой;
- вручную проверить: настоящий Telegram update проходит, curl без secret
  получает 401, cron c корректным заголовком отрабатывает;
- убедиться, что лог не содержит token/header value.

## 7. Вне scope

- RBAC и админ-панель для нескольких операторов;
- OAuth для внешних machine-to-machine интеграций;
- шифрование/ротация пользовательских ingest/widget token в БД;
- полный разбор Telegram handler на модули.

Эти пункты не нужны, чтобы закрыть текущие P0, и не должны задерживать релиз.
